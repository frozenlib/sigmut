# 履歴基盤の公開と SlabMap への適用

> 後続の名称変更により、公開モジュールは`change_feed`、公開型は`ChangeFeed*`、借用ガードは`ChangeFeedRef` / `ChangeFeedRefMut`、初回／差分を表すenumは`ChangeFeedDelta`となった。本文では設計・実装時点の名称を保持する。

## 目的

`SignalVec` / `StateVec` のために導入した履歴対応 Signal / State を、次の2方向へ拡張する。

- 外部 crate が `StateVec` のような履歴付きコレクション型を実装できる、簡潔で安全な public API を提供する。
- 共通基盤を「履歴管理」と「単一dependencyのリアクティブ通知」に分割する。`StateSlabMap`では`HistoryState`をマップ全体のStateとして再利用し、キー単位通知だけをSlabMap側に残す。`SignalSlabMap::from_scan`では履歴管理部分だけを再利用する。

先行計画の実装結果は `docs/plan_archive/2026-08-04_履歴対応SignalとStateの共通化.md` に残す。本計画は、その実装を破棄するものではなく、責務境界と公開境界を整理する後続作業とする。

## 現状と課題

現在の `history` モジュールには、次の2種類の責務が同居している。

1. 値、変更履歴、reader cursor、履歴保持数、不要履歴の解放を管理する責務。
2. `BindSource` / `BindSink` / `SinkBindings` を使って、State と scan を単一の reactive dependency として公開する責務。

`SignalVec` は全体で1つの dependency を持つため、現在の `HistorySignal` / `HistoryState` をそのまま利用できる。一方、`SignalSlabMap` は次の dependency を区別する。

- `item(key)` が登録するキー単位の dependency
- `items()` と reader が登録するマップ全体の dependency

この差を `HistoryModel` の通知ポリシーや変更先 slot として共通基盤へ追加すると、履歴管理がコレクション固有の通知方式を知ることになる。代わりに履歴管理をリアクティブ層から分離し、SlabMap固有のキー単位通知はSlabMap側に残す。State版の全体通知には単一dependency用の`HistoryState`を再利用し、scan版は履歴ストレージだけを共有する。

また、現在は `history` モジュールと主要型が crate-private である。外部 crate が同等の履歴管理を再実装せずに独自コレクションを作れるよう、単一 dependency 用の高水準 API を公開する必要がある。

## 設計方針

### 1. 履歴ストレージとリアクティブ層を分離する

内部実装を次の3層に分ける。

#### 履歴ストレージ層

リアクティブ runtime を知らず、次だけを扱う。

- 現在のモデル値
- モデル固有の変更列
- snapshot と編集ガード
- reader cursor の retain / advance / release
- reader に保持されなくなった変更の解放
- snapshot 生存中に発生した cursor 操作の遅延適用

`HistoryStorage<M>`、cursor、reader 操作キューなどの具体型は `pub(crate)` とし、公開 API には露出させない。

#### 単一 dependency のリアクティブ層

履歴ストレージを使い、現在の `HistorySignal<M>` / `HistoryState<M>` 相当の動作を提供する。

- borrow/read 時の dependency 登録
- State 編集後の notification
- scan source の更新と dirty 判定
- reader の read/peek 時の dependency 登録

この層は `StateVec` のような「値全体で1つの dependency」を持つ型向けの public facade とする。

#### コレクション固有のリアクティブ層

`StateSlabMap`は`HistoryState<SlabMapModel<T>>`を内包する。マップ全体のborrow、reader、変更時の全体通知は`HistoryState`へ委譲し、`item(key)`用のキー単位bindingだけをSlabMap側に残す。

`SignalSlabMap::from_scan`は、再計算後に変更されたkeyごとのdirty状態を更新する必要があるため、単一dependency用の`HistorySignal`は使用しない。既存の`SourceBinder`、キー単位と全体の`SinkBindingsSet`を維持し、内部の値・変更履歴・reader cursorだけを履歴ストレージ層へ委譲する。

これにより、共通基盤へキー単位通知機能を追加せずに履歴の重複実装を削除し、State側では公開`HistoryState`が実際のコレクション実装を簡略化できることも検証する。

### 2. public API は高水準 facade に限定する

`src/lib.rs` から `pub mod history` を公開する。外部 crate 向けに公開する主要型は次の7つに限定する。

```rust
pub trait HistoryModel: 'static {
    type Change: 'static;

    fn release_change(&mut self, change: Self::Change) {
        drop(change);
    }
}

pub struct HistoryState<M: HistoryModel> { /* private */ }
pub struct HistorySignal<M: HistoryModel> { /* private */ }
pub struct HistoryReader<M: HistoryModel> { /* private */ }
pub struct HistorySnapshot<'a, M: HistoryModel> { /* private */ }
pub struct HistoryEdit<'a, M: HistoryModel> { /* private */ }

#[must_use]
pub enum HistoryDelta<I> {
    Initial,
    Changes(I),
}
```

`HistoryModel::release_change` は、変更が履歴から外れるときにモデル固有の保持リソースを解放する。変更値を drop するだけで十分なモデルではデフォルト実装を使える。`VecModel` や `SlabMapModel` は、安定した参照先としてモデル内に保持した旧値をここで物理削除する。

次の内部型は公開しない。

- cursor と age
- `Changes` / `RefCountOps`
- `HistoryStorage` と保留 reader 操作
- `Slot` と通知ルーティング
- SlabMap のキー単位通知ポリシー
- 編集ガードを抽象化するためだけの内部 trait

公開型のフィールドもすべて非公開とし、内部表現を将来変更できるようにする。

### 3. State / Signal / Reader の公開操作

`HistoryState` は次の操作を提供する。

```rust
impl<M: HistoryModel> HistoryState<M> {
    pub fn new(initial: M) -> Self;
    pub fn to_signal(&self) -> HistorySignal<M>;
    pub fn reader(&self) -> HistoryReader<M>;

    pub fn borrow<'a, 'r: 'a>(
        &'a self,
        sc: &mut SignalContext<'r, '_>,
    ) -> HistorySnapshot<'a, M>;

    pub fn borrow_untracked(&self) -> HistorySnapshot<'_, M>;

    pub fn borrow_mut<'a>(
        &'a self,
        ac: &'a mut ActionContext,
    ) -> HistoryEdit<'a, M>;

    pub fn borrow_mut_loose(
        &self,
        ac: &mut ActionContext,
    ) -> HistoryEdit<'_, M>;
}
```

`HistorySignal` は次の操作を提供する。

```rust
impl<M: HistoryModel> HistorySignal<M> {
    pub fn from_scan(
        initial: M,
        f: impl FnMut(
            HistoryEdit<'_, M>,
            &mut SignalContext<'_, '_>,
        ) + 'static,
    ) -> Self;

    pub fn reader(&self) -> HistoryReader<M>;

    pub fn borrow<'a, 'r: 'a>(
        &'a self,
        sc: &mut SignalContext<'r, '_>,
    ) -> HistorySnapshot<'a, M>;
}
```

scan の更新関数には `HistoryEdit` を値で渡す。State の `borrow_mut` と scan の双方が同じ所有ガード型を使えるため、外部 crate の `ItemsMut` は State 用ガードと scan 用の借用ガードを区別する必要がない。

```rust
HistorySignal::from_scan(Model::new(), move |edit, sc| {
    let mut items = ItemsMut { edit };
    f(&mut items, sc);
})
```

scan node が更新後の dirty 判定を行うための完了状態は `HistoryEdit` の非公開フィールドを通して内部へ返す。外部 API に finish callback や通知型を公開しない。

`HistoryReader` は次の操作を提供し、clone 後は同じ cursor から独立して進む。

```rust
impl<M: HistoryModel> HistoryReader<M> {
    pub fn read<'a, 'r: 'a>(
        &'a mut self,
        sc: &mut SignalContext<'r, '_>,
    ) -> HistorySnapshot<'a, M>;

    pub fn peek<'a, 'r: 'a>(
        &'a self,
        sc: &mut SignalContext<'r, '_>,
    ) -> HistorySnapshot<'a, M>;
}
```

`HistoryState`、`HistorySignal`、`HistoryReader` は `M: Clone` を要求せずに `Clone` を実装する。現行 runtime と同様に `Rc` / `RefCell` ベースとし、`Send` / `Sync` は提供しない。

### 4. 初回読み取りを `HistoryDelta` で必須分岐にする

`HistorySnapshot` は次のAPIを提供する。

```rust
impl<M: HistoryModel> HistorySnapshot<'_, M> {
    pub fn current(&self) -> &M;

    pub fn delta(
        &self,
    ) -> HistoryDelta<impl Iterator<Item = &M::Change> + '_>;
}
```

`is_initial()` と `changes()` を別々には公開しない。両者を分けると、利用側が `changes()` だけを使い、初回の現在値全件を変更列へ変換する処理を忘れられるためである。

利用側は通常の exhaustive match で必ず2状態を扱う。

```rust
match snapshot.delta() {
    HistoryDelta::Initial => {
        // snapshot.current() から初回変更列を生成する。
    }
    HistoryDelta::Changes(changes) => {
        // cursor 以降の変更列を公開変更型へ変換する。
    }
}
```

`HistoryDelta` には `#[non_exhaustive]` を付けない。これにより `Initial` を処理しない通常の `match` はコンパイルエラーになる。具体的な iterator 型は戻り値の `impl Iterator` で隠し、公開 API は `Initial` と `Changes(iterator)` の2状態だけにする。

`HistoryDelta::Initial` は「変更が0件」ではなく「比較元のcursorがない」ことを表す。`HistoryDelta::Changes` の iterator は空になり得る。

### 5. 編集APIと変更記録の不変条件

`HistoryEdit` は次の最小操作を公開する。

```rust
impl<M: HistoryModel> HistoryEdit<'_, M> {
    pub fn current(&self) -> &M;
    pub fn current_mut(&mut self) -> &mut M;
    pub fn record(&mut self, change: M::Change);
}
```

外部 crate は通常、`HistoryEdit` を直接利用者へ公開せず、`ItemsMut` のようなコレクション固有 facade で包む。facade の各変更操作は、同じ編集ガード内で現在値の変更と `record` を必ず対にする。

```rust
fn insert(&mut self, index: usize, value: T) {
    let key = self.edit.current_mut().insert_raw(index, value);
    self.edit.record(ChangeData::Insert {
        index,
        new_value: key,
    });
}
```

`record` が1度も呼ばれなかった編集は通知せず、scan の dirty 判定も false とする。`current_mut` だけで現在値を変更すると履歴と通知が生成されないため、この不変条件を `HistoryEdit` とモジュールの rustdoc に明記する。

scan版SlabMapのキー通知に必要な「今回の編集で記録された変更」の参照はcrate-private APIとする。これは履歴ストレージの編集範囲を読む機能であり、公開`HistoryEdit`に通知機能を追加するものではない。`StateSlabMap`のinsert/removeでは操作対象のkeyが呼び出し側で既知なので、この内部APIを使わず、`HistoryState`の全体通知後に対象keyだけを明示的に通知する。

## `SignalVec` / `StateVec` への適用

公開化後も `SignalVec` / `StateVec` の外部 API は変更しない。

- `VecModel<T>` は `HistoryModel` を実装する。
- `StateVec<T>` は `HistoryState<VecModel<T>>` を包む。
- 変化する `SignalVec<T>` は `HistorySignal<VecModel<T>>` を包む。
- `SignalVecReader<T>` は `HistoryReader<VecModel<T>>` を包む。
- `Items<T>` は `HistorySnapshot<VecModel<T>>` を包む。
- `ItemsMut<T>` は所有する `HistoryEdit<VecModel<T>>` を包む。
- immutableな `Rc<Vec<T>>` / `&'static [T]` の専用経路は維持する。

`HistorySignal::from_scan` が編集ガードを値で渡す形へ変わるため、現在の `ItemsMutData::State` / `Direct` と `HistoryEditAccess` は削除し、State と scan の双方で同じ所有ガードを使う。

## `SignalSlabMap` / `StateSlabMap` への適用

### モデル

SlabMap固有の現在値と変更を次のように分離する。

```rust
struct SlabMapModel<T> {
    items: SlabMap<Item<T>>,
    len: usize,
}

enum SlabMapChangeData {
    Insert { key: usize },
    Remove { key: usize },
}
```

`Remove` は対象を直ちに `SlabMap` から削除せず、現在値から見えない墓石にする。変更を必要とするreaderが存在する間は旧値を同じkeyで保持し、`release_change(Remove)` で物理削除する。これにより `SlabMapChange::Remove { old_value }` の参照をreaderの保持期間中安定させる。

### Stateの構造

`RawStateSlabMap`は次の構成にする。

```rust
struct RawStateSlabMap<T> {
    state: HistoryState<SlabMapModel<T>>,
    item_sinks: RefCell<ItemSinkBindings>,
}
```

現在の`items: RefCell<ItemsMut<T>>`と`ref_counts: RefCell<RefCountOps>`は`HistoryState`へ統合する。State側のbinding集合はキー単位だけを保持し、マップ全体用の`any` bindingと`SLOT_ITEMS`の処理は`HistoryState`の単一dependencyへ委譲する。

これによりState側から次を削除する。

- `ItemsMut::edit_start`
- `ItemsMut::edit_end_and_notify`
- `ItemsMut::clean_changes`
- reader参照カウントの直接操作
- State用`SinkBindingsSet::any`
- `RawStateSlabMap`の全体slotに対する`BindSource`処理

### State編集

`StateSlabMap::insert` / `remove`は`HistoryState::borrow_mut`から編集ガードを取得し、`SlabMapModel`の更新と`record`を行う。編集ガードの終了時に`HistoryState`がマップ全体を通知し、その後にSlabMap側が操作対象keyだけを通知する。

```rust
pub fn insert(&self, value: T, ac: &mut ActionContext) -> usize {
    let key;

    {
        let mut edit = self.state.borrow_mut(ac);
        key = edit.current_mut().insert_raw(value);
        edit.record(SlabMapChangeData::Insert { key });
    } // HistoryStateがマップ全体を通知する。

    self.item_sinks
        .borrow_mut()
        .notify(key, DirtyLevel::Dirty, ac.nc());

    key
}
```

`remove`も同じ順序とする。`HistoryEdit`が`ActionContext`を保持している間はキー通知に同じcontextを使えないため、スコープまたは`drop(edit)`で編集ガードを明示的に終了してからキー通知を行う。

履歴が追加されなかった編集は`HistoryState`から全体通知されない。StateSlabMapの公開変更操作は1操作につき対象keyが明確なので、記録された変更列を通知先の判定に使う必要はない。

### Stateの読み取り

`items()`は`HistoryState::borrow`へ委譲し、返された`HistorySnapshot<SlabMapModel<T>>`を`Items<T>`で包む。これによりマップ全体のdependency登録を`RawStateSlabMap`から削除できる。

```rust
pub fn items<'a, 'r: 'a>(
    &'a self,
    sc: &mut SignalContext<'r, '_>,
) -> Items<'a, T> {
    Items::from_snapshot(self.state.borrow(sc))
}
```

`item(key)`はキー単位bindingをSlabMap側へ登録した後、`HistoryState`内部の現在値を未追跡で射影borrowする。既存の`Ref<'a, T>`戻り値を維持するため、次に相当するcrate-private APIを設ける。

```rust
// HistoryStateのcrate-private API
fn borrow_current_untracked(&self) -> Ref<'_, M>;
```

SlabMap側はこれを`Ref::map`して対象値を返す。このAPIは既存公開APIとの接続にだけ使い、外部向け`history` APIには公開しない。射影borrow中に履歴圧縮が保留された場合は、次のsnapshot、編集開始、reader操作で再試行する。

### scan更新

`SignalSlabMap::from_scan` は既存の `SourceBinder` と `SinkBindingsSet` を維持する。更新関数へ渡す `ItemsMut` の内部だけを履歴編集ガードへ置き換える。

- upstream notification時は従来どおり全bindingへ `MaybeDirty` を通知する。
- 再計算後は、実際に記録された変更のkeyだけをdirty更新する。
- 変更がなければ全bindingをcleanへ戻し、dirtyを伝播しない。

### reader

State由来のSlabMap readerは`HistoryState::reader()`が返す`HistoryReader<SlabMapModel<T>>`を利用する。read/peek時のマップ全体dependency登録、cursor保持、clone、drop、履歴解放は`HistoryReader`へ委譲する。

scan由来のSlabMap readerは履歴ストレージのcrate-private cursor readerを使い、dependency登録だけをscan node側で行う。

1. scanの現在値を最新化する。
2. scan nodeの`SLOT_ITEMS`へdependencyを登録する。
3. 共通cursorでsnapshotを取得する。
4. readならcursorを進め、peekなら進めない。

`SignalSlabMapReader`は内部enumまたはreader traitでState由来とscan由来の経路を隠蔽し、既存の公開型を維持する。`DynSignalSlabMap`には現在の`ref_counts()`を残さず、sourceに適したreaderを生成する内部メソッドを持たせる。

これにより、Stateでは高水準`HistoryReader`まで再利用し、scanではcursor管理だけを共有しながら、それぞれのdependency登録方式を維持する。

## public API の利用例

外部 crate の独自リスト型は、内部モデルを非公開のまま共通型で包める。

```rust
use sigmut::history::{
    HistoryDelta, HistoryEdit, HistoryModel, HistoryReader,
    HistorySignal, HistorySnapshot, HistoryState,
};

struct ListModel<T> {
    // 現在値と履歴参照中の値を保持する。
}

enum ListChangeData {
    Insert { index: usize, value: usize },
    Remove { index: usize, value: usize },
}

impl<T: 'static> HistoryModel for ListModel<T> {
    type Change = ListChangeData;

    fn release_change(&mut self, change: Self::Change) {
        if let ListChangeData::Remove { value, .. } = change {
            self.release_value(value);
        }
    }
}

pub struct StateList<T: 'static>(HistoryState<ListModel<T>>);
pub struct SignalList<T: 'static>(HistorySignal<ListModel<T>>);
pub struct SignalListReader<T: 'static>(HistoryReader<ListModel<T>>);
pub struct Items<'a, T: 'static>(HistorySnapshot<'a, ListModel<T>>);
pub struct ItemsMut<'a, T: 'static>(HistoryEdit<'a, ListModel<T>>);
```

外部 crate がcursor、参照カウント、reactive nodeを実装する必要はない。独自型に必要なのは次だけとする。

- 現在値と変更データを表すモデル
- `HistoryModel`の実装
- snapshot/editを公開コレクションAPIへ変換する薄いfacade

## モジュール構成案

```text
src/
  history.rs                  # public moduleのre-exportとmodule-level docs
  history/
    storage.rs                # pub(crate): storage, cursor, compaction
    snapshot.rs               # public: HistorySnapshot, HistoryDelta
    edit.rs                   # public: HistoryEdit
    reader.rs                 # public facade + crate-private cursor reader
    signal.rs                 # public: HistorySignal, scan node
    state.rs                  # public: HistoryState, state node
    tests.rs                  # 共通履歴と公開契約のテスト
  collections/
    vec.rs                    # 単一dependencyのpublic facadeを利用
    slab_map.rs               # storageのみ利用し固有通知を維持
```

実装量に応じてファイル数は調整してよい。ただし、公開 facade、履歴ストレージ、コレクション固有通知の責務境界は維持する。

## 実装手順

1. 現在の共通履歴テストと `SignalVec` テストで既存動作を固定する。
2. `HistoryCell`から履歴ストレージ、cursor管理、snapshot/editを分離し、reactive型を使わないテストを通す。
3. Stateとscanが同じ所有`HistoryEdit`を使えるようにし、scan更新関数へ編集ガードを値で渡す。
4. `HistoryModel`、`HistoryState`、`HistorySignal`、`HistoryReader`、`HistorySnapshot`、`HistoryEdit`、`HistoryDelta`をpublic化し、module-level docsと各不変条件を記載する。
5. `HistoryDelta`のexhaustive matchを使うdoc exampleを追加し、初回処理と差分処理を明示する。
6. `SignalVec` / `StateVec`を公開facadeと同じ経路へ移行し、`HistoryEditAccess`とState/scan別の編集adapterを削除する。
7. `SlabMapModel<T>`を実装し、`ItemsMut<T>`から独自の`Changes` / `RefCountOps`管理を取り除く。
8. `RawStateSlabMap`へ`HistoryState<SlabMapModel<T>>`を組み込み、items/reader/全体通知を委譲する。State側のbinding集合はキー単位だけに縮小する。
9. `StateSlabMap`のinsert/removeを`HistoryState::borrow_mut`へ移行し、編集終了後に操作対象keyだけをSlabMap側から通知する。
10. 既存の`Ref<T>`を返す`item(key)`を維持するため、crate-privateの現在値射影borrowを接続し、その間の履歴圧縮保留を検証する。
11. `SignalSlabMap::from_scan`を共通履歴ストレージへ移行し、変更keyごとのdirty更新と変更なしの場合のclean化を維持する。
12. `SignalSlabMapReader`をState用`HistoryReader`とscan用cursor readerへ分け、公開facadeで差を隠蔽する。初回、差分、clone、drop、旧値解放を検証する。
13. rustfmt、Clippy、全targetテスト、doc test、cargo doc、coverageを実行する。
14. 実装結果を追記し、完了した計画書を`docs/plan_archive`へ移動する。

## テスト計画

### 公開履歴API

- 外部crate相当のintegration testで、非公開モデルを包む独自State/Signal/Reader型を実装できる。
- `HistoryState`と`HistorySignal::from_scan`の双方で同じ`HistoryEdit`を所有するfacadeを使える。
- 初回readが`HistoryDelta::Initial`、2回目以降が`HistoryDelta::Changes`になる。
- `HistoryDelta::Changes`は変更0件でも成立する。
- reader clone後のcursorが独立する。
- peekがcursorを進めず、readが進める。
- 最後のreaderとsnapshotが解放された後に`release_change`が呼ばれる。
- `record`のないState編集とscan更新は下流へdirtyを伝播しない。
- rustdocからcursor、age、通知slotなどの内部型が露出しない。

### SignalVec回帰

- State、scan、immutable sourceの初回/差分/peek/clone契約。
- insert/remove/set/move/swap/sort/drainの順序とold/new値。
- remove/setの旧値がreader保持中に解放されない。
- serde形式とデシリアライズ後の初回read。
- `get_mut` / `IndexMut`が再導入されていない。

### SlabMap回帰と追加テスト

- 初回readが現在の全要素をInsertとして返す。
- insert/removeの差分順序、key、new/old値。
- removeされた値が最後のreader解除まで保持され、その後に解放される。
- readerがない場合は不要な墓石と履歴が速やかに解放される。
- 複数readerとclone readerが異なるcursor位置を保持する。
- `item(key)`の依存先は別keyの変更でdirtyにならない。
- `items()`とreaderの依存先は任意keyの変更でdirtyになる。
- State由来の`items()`とreaderが`HistoryState`の単一dependencyへ登録される。
- State編集終了時の全体通知と、その後の対象key通知が同じaction内で正しく統合される。
- `item(key)`の射影borrow生存中にreaderを進行またはdropしてもpanicせず、borrow終了後の次の圧縮契機で旧値を解放する。
- key 0を含む各keyのbindingが正しく登録される。
- scan再計算で変更がなければdirtyを伝播しない。
- scanのinsert/removeが変更keyと全体だけをdirtyにする。

## スコープ外

- 通常の`Signal<T>` / `State<T>`を履歴型で置き換えること。
- 公開APIでのキー単位notification policy。
- cursor、age、reader参照カウントの公開。
- history coalescingや変更列の圧縮最適化。
- `HistoryEdit::current_mut`で変更したが`record`しなかった操作の自動検出。
- `Send` / `Sync`対応。
- `SignalVec` / `SignalSlabMap`の既存公開APIやserde形式の意図的変更。

## 完了条件

- 履歴ストレージがreactive notificationから分離され、単独テストされている。
- 外部crateが公開された7型だけを使い、`StateVec`相当の単一dependency型を実装できる。
- 初回と差分は`HistoryDelta`のexhaustive matchで区別され、初回処理を忘れにくいAPIになっている。
- `SignalVec` / `StateVec`が公開facadeと同じ実装経路を使い、既存契約を維持している。
- `StateSlabMap`が`HistoryState`へ履歴、全体dependency、全体通知、readerを委譲し、SlabMap側にはキー単位bindingだけが残っている。
- `SignalSlabMap::from_scan`が共通履歴ストレージとcursor管理を利用し、独自のキー単位および全体通知を維持している。
- 履歴を保持するreaderがなくなった後、VecとSlabMapの旧値が正しく解放される。
- 全テスト、Clippy、rustfmt、doc test、cargo docが成功する。
